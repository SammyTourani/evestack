## Storage and recall

The Postgres storing your durable sessions is already running, and `docker-compose.yml` uses
the `pgvector/pgvector` image — so the storage side of long-term memory costs one
`CREATE EXTENSION` and zero new containers. The agent gets `remember` and `recall` tools out of
the box (`agent/tools/remember.ts`, `agent/tools/recall.ts`).

```
"Remember this for the future: my production database runs on port 5433
 and I always deploy on Fridays."
```

...saved in one session, comes back correctly in a completely fresh one:

```
"Your production database runs on port 5433, and you deploy on Fridays."
```

## It needs an embeddings provider, and Anthropic is not one

Storage is free; turning text into a vector is not automatic. `lib/memory.ts` resolves the
embedding model from your chat provider. The template supports OpenAI or Ollama for embeddings; its other chat-provider paths require a separate embedding configuration:

| `EVESTACK_PROVIDER` | Embeddings | Model, vector width |
| --- | --- | --- |
| unset, or `openai` | yes, same key | `text-embedding-3-small`, 1536 |
| `ollama` | yes, but **a second `ollama pull`** | `nomic-embed-text` (274 MB), 768 |
| other template chat providers | separate embedding provider | uses OpenAI if `OPENAI_API_KEY` is set, or explicit `EVESTACK_EMBED_PROVIDER=ollama` |

On `anthropic` with no `OPENAI_API_KEY`, `remember` and `recall` do not work. The first call
fails with the fix in it:

```
EVESTACK_PROVIDER=anthropic has no embeddings endpoint, so long-term memory needs one from
somewhere else. Either set OPENAI_API_KEY, or run embeddings locally with
EVESTACK_EMBED_PROVIDER=ollama (then `ollama pull nomic-embed-text`).
```

That is deliberately a tool failure and not a boot failure — the agent, its sandbox and its
durable sessions all still work, because a project that cannot do embeddings is an ordinary
configuration rather than a broken one. `npm run verify` says the same thing before you find
out from a tool call.

On `ollama`, the embedding model is a **separate pull from the chat model**:

```bash
ollama pull nomic-embed-text
```

Miss it and `remember` fails on a model Ollama does not have. `npm run verify` checks for it by
name.

## The three variables

Set nothing here and embeddings follow `EVESTACK_PROVIDER`, which is right almost always. The
overrides exist for the Anthropic case above, and for a different embedding model:

| Variable | Default | What it does |
| --- | --- | --- |
| `EVESTACK_EMBED_PROVIDER` | follows `EVESTACK_PROVIDER` | `openai` or `ollama`. This is the one that makes memory work on the Anthropic path |
| `EVESTACK_EMBED_MODEL` | `text-embedding-3-small` / `nomic-embed-text` | the embedding model to call |
| `EVESTACK_EMBED_DIMENSIONS` | 1536 / 768 | the vector width, which must match what that model returns |

Model and width go together, and the width is baked into `evestack.memories` at creation. Vectors from different models are not comparable. Restore the original model and dimensions when a mismatch appears. To change models, [back up the database](/docs/self-hosting#backups) and plan a migration that recomputes vectors from the saved text while preserving owners, tags and source metadata. The dashboard does not automate that migration.

`lib/memory.ts` checks the column width on the first memory call and reports both dimensions. Width alone cannot detect a different model with the same dimensions; retain the original provider/model configuration with your backups. Do not discard the memory table to resolve a configuration mismatch.

## Review and correction in the dashboard

**Knowledge → Memory** shows the recorded owner, `shared` tag and source task. This is the installation operator's view across owners; dashboard sign-in does not provide per-person access control. Legacy rows retain an unknown owner rather than being relabelled as the operator's.

The template's default `EVESTACK_MEMORY_SCOPE=owner` recalls a caller's own records, records tagged `shared`, and legacy records with no owner. `strict` excludes the legacy records. `shared` makes the table available across callers. Custom agent code can implement a different policy.

Expand a record to mark it reviewed, stale, conflicting, or to save a proposed correction with a reason. Reviews are tied to the record's content, owner and database version. A changed record reopens review; a stale screen cannot save a review or delete that changed record. Each record shows its latest 20 reviews.

A proposal **does not change recall**. Use **Prepare correction task** to review a request for the agent's supported memory tools to regenerate the embedding and verify the result within the caller's existing permissions. The dashboard does not directly edit memory text or apply the correction automatically. Inspect the resulting task and memory records before treating it as corrected.

Removing a memory and writing its deletion audit are one transaction: an audit failure rolls removal back. API clients can send the displayed record hash as `If-Match` to `DELETE /api/memories/:id`; the dashboard always does this. Existing API callers that omit the header keep unconditional operator deletion semantics.

Authenticated API clients can read `GET /api/memories?q=invoice&limit=50&offset=0` and `GET /api/memories/:id` for the same content, ownership, source and record hash. `GET /api/memories/:id/review` returns the latest 20 reviews; `POST` requires the current hash, a verdict and a reason. Proposal text is stored only when the verdict is `correction_proposed`. Embeddings are never included in these responses.

Memory records have no automatic expiry in the template. Deletion removes a record from recall; its audit copy, review notes and proposal snapshots remain in Postgres and backups. These records identify the shared installation credential or recorded proxy attribution, not a verified individual teammate. The additive review tables remain available to a database operator after rollback to an older dashboard; old dashboards do not enforce the new record preconditions.

## HNSW, not IVFFlat — a correctness fix, not a preference

We built this with an IVFFlat index first, because it's the more commonly recommended default.
It silently broke memory.

IVFFlat assigns vectors to `lists` centroids **at index-build time**. Build it on an empty
table — which any bootstrap migration must, since memory starts with nothing in it — and the
centroids are meaningless. The planner switches to the index once a query looks selective
enough, probes a near-empty list, and returns **zero rows** for a query that plainly should
match.

We reproduced this exactly: the same `recall()` call returned **2 results at `LIMIT 3`** and
**0 results at `LIMIT 20`**, purely because the query plan flipped between them.

```sql
-- lib/memory.ts uses this, not ivfflat:
CREATE INDEX memories_embedding_idx
ON evestack.memories USING hnsw (embedding vector_cosine_ops)
```

HNSW builds a navigable graph incrementally and needs no training data — it's correct from the
first row, which is what an empty-by-definition memory table needs.

## Tags and filtering

`remember` accepts optional tags; `recall` can filter by them. The agent chooses its own tags —
in testing, saving a deployment preference produced `["preference", "devops", "deployment"]`
without being told to.
