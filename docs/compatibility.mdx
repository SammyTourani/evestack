A distribution's product is not the framework. It is a **tested combination** — a set of
versions someone has actually run together, with a mechanical way to prove the claim is still
true tomorrow. This page is that claim for evestack.

## The combination evestack ships

| Package | Declared as | Where |
| --- | --- | --- |
| `eve` | `^0.30.6` | `templates/default/package.json` |
| `eve` (peer range) | `>=0.30.0 <1.0.0` | `@evestack/budget`, `@evestack/composio`, `@evestack/sandbox-opensandbox` |
| `@workflow/world-postgres` | `beta` → resolves to `5.0.0-beta.31` | `templates/default/package.json` |
| `ai` | `^7.0.38`, plus an `overrides` entry pinning the whole tree to it | `templates/default/package.json` |
| Node | `>=24` | `engines` in every manifest |

`^0.30.6` is a caret on a `0.x` version, so it admits `0.30.7` and refuses `0.31.0`. That is
the intended reading: eve is pre-1.0, and pre-1.0 a breaking change lands in a **minor**
version. Widening that range by hand is how you ship an untested framework to everyone who ran
`npx create-evestack`.

`packages/create-evestack` does not declare its own eve range. Its `template/` directory is
generated from `templates/default` at `prepack` by
`packages/create-evestack/scripts/sync-template.mjs` and is gitignored, so the version a
scaffolded project installs is the template pin by construction rather than by anyone
remembering to update a second file.

## How the pinned version was chosen

Not by reading a release announcement. `.github/workflows/eve-watch.yml` asks npm for the
latest eve every morning, bumps every manifest that pins it on a branch, installs, typechecks,
runs the contract suite, and opens a pull request reporting all of it. A human merges it — the
job has no auto-merge and never will. The pin above is the newest eve that came through that
process green; [Upgrading eve](/docs/upgrading#the-eve-watch-workflow) describes the job.

The cadence is the reason it is a job and not a habit. eve published `0.30.0`, `0.30.1`,
`0.30.2`, `0.30.3`, `0.30.4`, `0.30.5` and `0.30.6` **on the same day** — seven releases inside
nine hours, per the npm publish timestamps recorded in `contract/history/`.

One contract exists purely to keep this page honest:
`version/installed-satisfies-every-declared-range` asserts that the single eve actually
installed satisfies all **seven** eve ranges this repo declares across four manifests — the
template's dependency, and a `devDependencies` plus `peerDependencies` pair on each of the
three publishable packages. A bump that updates one manifest and forgets another resolves fine
here and fails at `npx create-evestack`; this contract fails first instead.

## What is verified

The suite in `contract/` is deterministic, offline and free: it reads the installed eve
package and nothing else — no model call, no database, no Docker daemon, no network — and runs
in well under a second. That is what makes it affordable to run against every release eve
ships.

## What a green suite does not prove

Read the "What it pins" column literally. Green means every assumption in that column still
holds against the installed package. It means:

- the `eve/*` subpaths evestack imports resolve, and the values it binds are still exported
- the `$eve.*` run attributes the dashboard reads out of Postgres are still what eve writes
- `localDev()` refuses to grant on anything the caller controls; `httpBasic()` fails closed
- the session, cancel and stream routes the dashboard drives exist, with the same content type
- `approval` is still the gating field, and `SandboxBackend` still has the shape we duck-type

It does **not** mean the release works. Nothing here runs a model, spends a token, opens a
socket, or drives a session end to end. A contract can only fail on an assumption somebody
wrote down.

<Warning>
  This is not hypothetical. On 2026-08-05 a live smoke test of the 0.30.2 → 0.30.6 upgrade
  found that **denying** a tool approval killed the durable session: eve records the denied
  call with `output.type = "execution-denied"`, the AI SDK's tool-output contract has no such
  type, and `@ai-sdk/openai` emitted `output: undefined` — a provider 400 that took the session
  down with it (`step.failed → turn.failed → session.failed`). The contract suite — 169
  assertions at the time — was green on **both** versions, and had been all along. The bug was
  never a regression; approval had only ever been verified as far as the card resolving.
</Warning>

The fix shipped as a `wrapLanguageModel` middleware in `templates/default/agent/agent.ts`. The
standing rule is that when something breaks past the suite, the deliverable is the contract
that would have caught it, in the same pull request —
[Upgrading eve](/docs/upgrading#when-it-stays-green-and-something-breaks-anyway) has the
reasoning.

## Two version traps

### `@workflow/world-postgres` must be pinned to `beta`

The durable-session world speaks a protocol version, and the eve runtime **rejects a mismatched
one at boot** rather than degrading. npm's `latest` tag on `@workflow/world-postgres` points at
the 4.x line (`4.3.3` when we recorded it); eve needs the `5.0.0-beta` line.

<Warning>
  The pin is the dist-tag — `"@workflow/world-postgres": "beta"` — not `latest`, and not a
  caret range, which would resolve to 4.x and never reach a prerelease. Get it wrong and the
  project fails on its first boot with a protocol version error that does not name the tag. See
  [Troubleshooting](/docs/troubleshooting).
</Warning>

`templates/default` declares the `beta` tag; the committed lockfile resolves it to
`5.0.0-beta.31`.

### eve `0.30.0` is a security floor, not a convenience one

The peer range on every publishable evestack package starts at `>=0.30.0` because `0.29.x` had
an authentication bypass. `localDev()` decided "is this request from my own machine" by
matching an unanchored `/^127\./` against the request URL's hostname — and in a server that
hostname comes from the client's `Host` header. `127.evil.com`, a name anyone can register and
point at your agent, received a full local-dev principal with no credentials. eve fixed it
upstream in `0.30.0` by deciding from the process instead of the request.

That is recorded, not remembered: `contract/history/eve-0.29.5.json` has
`auth/local-dev-must-not-trust-the-request` red, and every `0.30.x` report has it green. You
can watch the assertion do its work:

```bash
EVESTACK_CONTRACT_EVE_DIR=path/to/an/eve-0.29.x node contract/run.mjs --only=auth
```

Do not widen a peer range below `0.30.0` to make an install resolve.

## When the table goes red

A red contract is a decision, not a bug — sometimes eve changed deliberately, sometimes it
regressed, sometimes the contract was over-specified and describes an accident rather than a
dependency. Those three outcomes need different fixes, and picking the wrong one is how a
suite quietly stops meaning anything.

## Which eve docs describe your pin

<Note>
  For an installed project, `node_modules/eve/docs/` is the documentation for the exact version
  you resolved — eve ships it inside the package. [eve.dev](https://eve.dev/docs) always
  documents latest, which at this cadence can be several releases ahead of your lockfile. When
  the two disagree about a default, the copy in `node_modules` is the one that will run.
</Note>

[Upstream eve](/docs/upstream) covers how to use that local copy and why these docs link the
framework instead of mirroring it.
