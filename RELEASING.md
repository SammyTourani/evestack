# Releasing

Eve Stack publishes seven npm packages and one dashboard image. Packages are independently
versioned. `release-manifest.json` records the selected combination for this checkout;
it does not prove publication or deployment.

| Artifact | Directory | Distribution |
| --- | --- | --- |
| `@evestack/budget` | `packages/evestack-budget` | npm; generated-project dependency |
| `@evestack/composio` | `packages/evestack-composio` | npm; generated-project dependency |
| `@evestack/schedules` | `packages/evestack-schedules` | npm; generated-project dependency |
| `create-evestack` | `packages/create-evestack` | npm; carries the project template |
| `evestack` | `packages/evestack-cli` | npm; depends on the scaffolder and carries matching setup instructions |
| `@evestack/mcp` | `packages/evestack-mcp` | npm; standalone dashboard client |
| `@evestack/sandbox-opensandbox` | `packages/sandbox-opensandbox` | npm; optional sandbox backend |
| `@evestack/dashboard` | `packages/dashboard` | GHCR container image; private npm package |

`packages/website` and `templates/default` remain private npm packages. The template ships
inside `create-evestack`; the website follows its deployment process.

## Prepare the candidate

1. Review `RELEASE_PLAN.md`, the complete PR diff and `CHANGELOG.md`. Separate passing fixture
   checks from a live model/source result, external notification receipt and first-user testing.
2. Bump changed artifacts and update the template's component dependencies, the CLI's scaffolder
   dependency, dashboard image pins and lockfile together. Do not republish an unchanged version.
3. Generate and check the component manifest, then regenerate template and registry artifacts:

   ```bash
   node scripts/release-manifest.mjs
   node scripts/release-manifest.mjs --check
   node packages/create-evestack/scripts/sync-template.mjs
   node packages/evestack-cli/scripts/sync-skill-pack.mjs
   node registry/build.mjs
   ```

4. Run the required build/typecheck/test/compatibility checks and inspect every CI job on the
   exact candidate commit, including non-blocking Windows/macOS and the dashboard image job.
   Confirm the native PostgreSQL restore test uses pgvector without a skip. Check dependencies
   with `pnpm audit --prod`; investigate findings rather than treating an old report as current.
5. Pack with `pnpm pack` from each package directory. Inspect the actual tarballs: resolved
   dependency versions, README/LICENSE, template manifest, CLI setup-pack fingerprints, and no
   credentials or generated local state. A green source build is not proof a tarball installs.
6. Rehearse a clean installed CLI, generated project install, typecheck and build using the
   candidate tarballs. If unpublished prerequisites are served from a local registry fixture,
   record that limitation. Repeat the public-registry check after publication.
7. Document upgrades, backups and remaining operating limits. Prepare release notes with
   concrete behavior, validation and limitations; do not claim perfect safety or correctness.

The source-controlled `release-manifest.json` must be committed. Template copies and the CLI's
`agent-pack.json` are regenerated by prepack and stay ignored. The setup pack is built from a
fixed list under `skills/evestack`, versioned with the CLI and verified when loaded. A custom
`EVESTACK_PACK_URL` explicitly opts out of the bundled version match.

## Publish in dependency order

Publish only reviewed commits on `main`, after the candidate checks and release decision.
Pushing the release tags below starts publishing workflows; it is not a preview.

1. **Changed template dependencies:** budget, Composio and schedules. Query npm for each exact
   required version and wait until it resolves. Leave already-published unchanged versions alone.
2. **Dashboard image:** publish the candidate image before releasing a scaffolder that requests
   it. Verify the versioned multi-architecture manifest and inspect the publication result.
3. **`create-evestack`:** release after its template prerequisites and dashboard image exist.
4. **`evestack`:** release after its exact scaffolder dependency exists on npm.
5. **MCP and OpenSandbox:** release independently after their own checks pass.

The version in `packages/dashboard/package.json`, generated/root Compose image pins and release
manifest must agree. The image's PR workflow runs the container on amd64; publication builds
amd64 and arm64. Check the actual published artifacts rather than assuming a tag made them available.

## Tag convention and workflows

Use an annotated `<package>@<version>` tag that matches the package manifest. Keep existing
public tags immutable. Do not reuse a version to change its contents.

```bash
# Replace the placeholders with the reviewed package and manifest version.
git tag -a 'PACKAGE@X.Y.Z' -m 'Release PACKAGE X.Y.Z'
git push origin 'PACKAGE@X.Y.Z'
```

For the dashboard the package name is `@evestack/dashboard`. New dashboard releases use that
convention; historical `dashboard-v*` tags remain supported only for old release operations.

[Publish npm](.github/workflows/publish-npm.yml) validates the tag, manifest, main ancestry and
published prerequisites. One job builds/tests/packs without publication credentials; a separate
job publishes the resulting tarball through npm OIDC with provenance and lifecycle scripts disabled.
`pnpm pack` resolves `workspace:*` dependencies. Do not publish an unpacked workspace with npm.

[Publish dashboard](.github/workflows/publish-dashboard.yml) validates image/version pins and
publishes to GHCR. Its overwrite option changes an existing public artifact and is exceptional;
prefer a new version. The [image check](.github/workflows/dashboard-image.yml) is verification,
not publication.

For a workflow retry, inspect the failed stage first and select the existing release tag.
If npm accepted the upload but the version has not materialized, wait and recheck the exact
version. Do not immediately publish again, move the tag, or burn a replacement version.

## npm account prerequisites

Each public package needs its GitHub trusted publisher configured for this repository and
`publish-npm.yml`, plus the intended package publishing MFA policy. Inspect current npm settings
when changing the workflow identity. These are per-package settings, not properties a source
commit can establish. Never put registry tokens in the repository or generated project.

## Verify from a new user's position

After each publication, verify the exact version and tarball metadata from npm. Once all
prerequisites resolve, install the exact new CLI in a clean directory and scaffold a project.
Check the dashboard image pull, model request, repository access and resulting evidence with
bounded usage. Test any promised channel through actual receipt. Record the versions used.

```bash
npm view 'PACKAGE@X.Y.Z' version dist.integrity
npx --yes --package='evestack@X.Y.Z' evestack --version
```

Inspect `gh release list` and the published package/image before creating a release page.
Use the exact existing tag and concrete notes; a changelog heading or draft release page does
not mean a package is available. Read current registry state instead of maintaining a count of
all historical tags, releases or published versions in this document.

## Upgrade and recovery notes

Explain which processes must upgrade together, which schemas are additive, and how to verify
activation. Preserve Postgres and private configuration. Do not drop schemas to bypass guards.
A restored database can contain pending jobs that repeat external actions: inspect it without
workers, then deliberately decide what may resume. Link users to [backup and restore](docs/backup-restore.mdx),
[upgrading](docs/upgrading.mdx), [operations](docs/operations.mdx) and [removal](docs/uninstall.mdx).
