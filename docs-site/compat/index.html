What a contract is

Not a type check. An executable assertion about what eve does.

evestack is a distribution built on top of eve, so every line of it rests on assumptions about eve's behaviour. A contract writes one of those assumptions down as code that runs against the real installed eve package and either holds or does not. auth/local-dev-must-not-trust-the-request, for instance, hands eve's localDev() a request whose Host header claims to be 127.evil.com and asserts that no principal comes back.

There are 16 of them and 231 assertions. The whole suite runs in well under a second: no mocks, no model calls, no network, no database, no Docker. That is what makes it affordable to run against every single eve release rather than the one we happen to ship.

Two numbers, one suite. The verdict above counts 15 contracts and 219 assertions; this paragraph and docs/compatibility.mdx count 16 and 231. The difference is exactly version/installed-satisfies-every-declared-range, whose 12 assertions describe evestack's own manifests rather than eve — see below. Both figures are computed from the same reports in contract/history/; neither is typed by hand.

A skip is the third outcome and is not a pass: 9 of the 10 recorded runs skipped at least one contract (0.29.5–0.30.7), which is what the ⊘ cells in the matrix mean. They are excluded from both counts above, not counted green.

Why this page exists

eve moves fast — 7 releases went out on 4 Aug 2026 alone. The fair criticism of anything built on top of it is that it will quietly rot: a wrapper that compiles perfectly against a framework that no longer means what it used to. So the claim evestack makes is not "we keep up". It is this table, and the reports behind it, which you can regenerate yourself.

The history is not decoration either. evestack once shipped a strictLocalDev() wrapper because eve 0.29.x decided "is this request from my own machine" from the request's own Host header — so 127.evil.com, a name anyone can register, was handed a full local-dev principal with no credentials. eve 0.30.0 fixed it upstream, and from that moment our wrapper could add no protection and would reject legitimate access over a LAN IP or a tunnel. It typechecked perfectly on both days. Nothing about its types ever changed — only what eve meant. eve 0.29.5 stays on this page as the control: proof that the suite can actually go red.

Why one red row is not a break

The row marked bookkeeping, not eve asks whether the eve under test satisfies the version ranges evestack's own manifests declare today. Every release older than the current pin fails it by construction — that is a fact about our package.json files, not about eve. Only the 15 API contracts above it describe eve itself, and the headline verdict counts those alone.

What went red, exactly

The failing assertion, what evestack assumed, and what breaks because of it — straight out of the recorded reports.

eve 0.29.5 1 API contract broken eve changed under us here

auth/local-dev-must-not-trust-the-request 6 of 9 assertions failed

What evestack assumed: localDev() decides from the running process (EVE_DEV / vercel dev), and no Host header or URL hostname can make it grant.

  • ✗ localDev() denies a request claiming to come from "127.evil.com"expected no principalactual principal local-dev (type local-dev, via local-dev)
  • ✗ localDev() denies a request claiming to come from "127.0.0.1.evil.com"expected no principalactual principal local-dev (type local-dev, via local-dev)
  • ✗ localDev() denies a request claiming to come from "127.0.0.1.nip.io"expected no principalactual principal local-dev (type local-dev, via local-dev)
  • ✗ localDev() denies a request claiming to come from "evil.localhost"expected no principalactual principal local-dev (type local-dev, via local-dev)
  • ✗ localDev() still grants inside an `eve dev` process, regardless of the request's hostexpected a local-dev principalactual no principal
  • ✗ the dev grant is still a `local-dev` principalexpected "local-dev"actual undefined

What this breaks in evestack: templates/default/agent/channels/eve.ts puts `localDev()` first in the auth chain of every scaffolded agent, so that `eve dev` needs no credentials on your own machine, with HTTP Basic underneath it for everything else. Every evestack agent is therefore exactly as exposed as localDev() is permissive. If eve reintroduces a request-derived grant, anyone who can reach the agent's port gets an unauthenticated local-dev principal — full session creation, full tool execution — by sending a Host header. That is a remote authentication bypass in the default template, and it is what eve 0.29.5 actually shipped. See the long comment in that file for the history.

Check it yourself

The point of the page is that you do not have to take its word.

git clone https://github.com/SammyTourani/evestack && cd evestack
pnpm install

# the eve we ship, in under a second
node contract/run.mjs

# any published release you like — downloads the tarball, touches no node_modules
node contract/record.mjs --npm=0.29.5 --dry-run

# rebuild this page from the committed reports
node contract/render-compat.mjs

Each report in contract/history/ records the npm integrity hash of the exact tarball that was tested, so a row cannot be quietly re-pointed at a different build.
